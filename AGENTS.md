# Architecture rules
- Partner progress is validated and stored separately from local order status; only signed status responses supply arrival, and bounded polling applies persisted changes without reviving recalled or cancelled orders.
- Customer home-screen installation uses a separate manifest identity and ride-code start URL selected by pathname; staff retain their original manifest, and no app-shell service worker is introduced.
- Both customer tracking responses expose live driver data only for assigned active rides; closed ride codes retain their receipt/status without becoming permanent GPS links.
- Read policies require taxi membership for shared chat identity and vehicles; ordinary drivers read only their own or active-SOS locations, and only dispatchers download vehicle photos directly, preserving private storage and existing helper restrictions.
- Account-dependent effects keep a stable user identity across permission refreshes; native GPS uses one background watcher and live orders, financial lists, maps, SOS and customer status refreshes coalesce with deadlines and dispose stale reads, so renewal cannot restart Android tracking or strand stale lists.
- Driver acceptance updates the visible order only from the persisted write response; sign-out clears protected query state and ends the local device session before replacing navigation, preventing delayed feedback and back-navigation into cached work.
- Helper dispatch access is stored separately from profiles and checked by restrictive database read policies; only a protected atomic database function lets the main dispatcher change it, preventing UI bypass and privilege escalation.
- Dispatcher and helper order entry reuse one form; helpers retain driver access to their own work but never receive driver recommendation or full-dispatch data.
- Customer arrival uses a separate pickup-departure timestamp that supersedes manual ETA, authenticated assigned-driver writes, and a shared server-only one-minute Routes claim refreshed by drivers or validated customer tracking codes; passenger-trip status and public position polling never trigger billable ETA calls, so ETA continues when the driver screen is closed.
- Dispatcher assistance lives in focused UI components and authenticated server functions; server-only modules own AI calls and read live data with the caller's permissions, so recommendations cannot grant privileges or silently alter orders.
- Voice uploads use a size-bounded, dispatcher-authorized streaming server route and complete PCM WAV recordings, so web and Android recordings remain decodable.
- Driver recommendations use tariff capacities and fresh locations with deterministic distance ranking, so seating and availability are not invented by AI.
- Translator voice uses authenticated, bounded WAV uploads and streamed PCM speech; completed audio is reused within the open panel to avoid billing again on replay.
- Translator language and voice rules live in a shared browser-safe settings module; voice preference is stored per account locally and audio cache keys include voice, avoiding gender inference and incorrect cached playback.
- Partner-forwarded orders are hidden from drivers and helpers by a restrictive database policy, so the UI cannot leak them.
- Android releases use android-release.json, applied after platform generation and verified against the APK; changing it triggers GitHub Actions so regenerated native files cannot silently revert the installed version.
